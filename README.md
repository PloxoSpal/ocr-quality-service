# OCR Quality Service

HTTP-сервис, который проверяет, пригодно ли изображение документа для OCR. Принимает картинки (PNG, JPEG, WebP, TIFF, BMP) и PDF, возвращает вердикт `suitable_for_ocr`, оценку `quality_score` от 0 до 1, список проблем и результат каждой проверки.

## Быстрый старт

```bash
docker compose up --build
```

Сервис поднимется на <http://localhost:8000>, Swagger доступен на <http://localhost:8000/docs>.

```bash
curl -s -F file=@dataset/images/image_002.jpg localhost:8000/analyze
```

```json
{
  "suitable_for_ocr": false,
  "quality_score": 0.7016,
  "issues": ["skew: text is rotated by -13.4° (limit ±5°)"],
  "checks": {"skew": {"passed": false, "score": 0.0, "value": -13.45, "...": "..."}, "...": "..."},
  "processing_time_ms": 41.2
}
```

Без Docker: `uv sync && make run`. Тесты, оценка на наборе данных и benchmark описаны в [RUNBOOK.md](RUNBOOK.md).

## API

| Метод | Что делает |
|---|---|
| `POST /analyze` | `file` — картинка или PDF; `checks` — необязательно, через запятую (`blur,skew`), по умолчанию все |
| `GET /checks` | список проверок |
| `GET /health` | жив ли сервис |

Для PDF каждая страница проверяется отдельно, в ответе есть `pages` и общий итог `summary`.

Ошибки приходят в виде `{"detail": "..."}`: 400 — пустой файл, 413 — слишком большой, 415 — не картинка и не PDF, 422 — битый файл или неизвестная проверка, 503 — сервис перегружен.

## Проверки

| Проверка | Что меряет | Граница | Критичная |
|---|---|---|---|
| `blur` | ширина размытия края букв | 1.2 px | да |
| `skew` | угол строк | 5° | да |
| `resolution` | высота буквы в пикселях | 5.5 px | да |
| `contrast` | разница яркости чернил и бумаги | 0.10 | да |
| `text_presence` | сколько символов сложилось в строки | 35 | да |
| `exposure` | не слишком ли тёмная бумага или бледные чернила | — | нет |
| `noise` | пылинки и зернистость фона | — | нет |

**Итог.** `quality_score` — взвешенное геометрическое среднее оценок проверок: одно очень плохое свойство портит OCR, как бы хороши ни были остальные. Страница пригодна, если не провалена ни одна критичная проверка и `quality_score >= 0.6`.

**Калибровка.** Пороги подобраны по результатам Tesseract на выданном наборе данных. С ручной разметкой совпадают 46 из 46 изображений (4 пограничных случая не считались), подробности — в `eval/reports/evaluation.md`. Совпадение получено на тех же данных, на которых подбирались пороги.

## Производительность

Apple M5, 10 ядер: около 36 мс на изображение в одном процессе и около 130 изображений в секунду по HTTP на пуле из 10 процессов. При перегрузке лишние запросы сразу получают 503, а принятые обслуживаются без замедления.

## Как устроено

```
src/ocr_quality/
├── api.py         эндпоинты
├── services.py    пул процессов и лимит запросов (503)
├── analyzer.py    прогон проверок и итоговая оценка
├── page.py        поиск текста на странице: делается один раз для всех проверок
├── files.py       чтение картинок и PDF
├── checks/        по файлу на проверку
├── schemas.py     формат ответов
├── config.py      настройки (WORKERS, MAX_REQUESTS, MAX_UPLOAD_MB)
└── errors.py      ошибки и их HTTP-коды
```

Анализ занимает процессор, поэтому выполняется в пуле процессов: так используются все ядра, а сервер тем временем принимает другие запросы.

Новая проверка — это класс-наследник `Check` с методом `measure` в `checks/` и одна строка в `ALL_CHECKS`.

## Ограничения

- Поворот на 90° и 180° не определяется: наклон ищется в пределах ±45°.
- Перспектива, блики и перекрытия не проверяются.
- PDF с текстовым слоем анализируется как картинка; у многостраничного TIFF проверяется только первая страница.
