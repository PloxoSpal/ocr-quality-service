# OCR Quality Service

HTTP-сервис, который проверяет, пригодно ли изображение документа для OCR. Он прогоняет семь проверок качества (размытие, наклон, разрешение, контраст, наличие текста, экспозиция, шум) и возвращает:
- результат каждой проверки;
- итоговую оценку `quality_score` от 0 до 1;
- вердикт `suitable_for_ocr`;
- список проблем простым текстом;
- время обработки.

Принимает изображения (PNG, JPEG, WebP, TIFF, BMP) и многостраничные PDF: каждая страница проверяется отдельно, документ получает общий итог.

Как запустить и проверить — в [RUNBOOK.md](RUNBOOK.md).

```bash
uv sync && make run
curl -s -F file=@OCR_team_developer_task/datatset/images/image_002.jpg localhost:8000/analyze
```

## Что реализовано

| Требование ТЗ | Как сделано |
|---|---|
| `GET /checks`, `POST /analyze` | `api.py`; ответ содержит результат каждой проверки, итоговую оценку и время |
| Не меньше 3 проверок разного типа | 7 проверок шести типов: резкость, геометрия, разрешение, фотометрия (контраст, экспозиция), шум, содержимое |
| Новые проверки без переделки остального | файл с классом в `checks/` и одна строка в списке `ALL_CHECKS` |
| Неверный ввод и неизвестные проверки | понятные ошибки с кодами 400, 413, 415, 422, 503, 504 |
| Замер времени, benchmark | `processing_time_ms` и `timings` в каждом ответе, `scripts/benchmark.py`, [результаты ниже](#производительность) |
| Тесты, README, RUNBOOK, docstring | 74 теста; docstring обязательны (проверяет ruff) |
| **Доп. уровень 1:** PDF | каждая страница проверяется отдельно, есть итог по документу и время всего документа |
| **Доп. уровень 2:** конкурентность | пул процессов, лимит запросов внутри сервиса, 503 при переполнении, нагрузочный benchmark |

## Как устроено

```
src/ocr_quality/
├── main.py        создаёт приложение FastAPI: эндпоинты, сервис анализа, ответы с ошибками
├── api.py         слой api: эндпоинты GET /checks, POST /analyze, GET /health
├── services.py    слой services: проверка запроса, лимит нагрузки, запуск анализа в пуле процессов
├── schemas.py     слой schemas: формат результатов и ответов API
├── analyzer.py    прогон проверок по странице и итоговая оценка страницы и документа
├── page.py        подготовка страницы: где на ней текст, какого он размера, где бумага
├── files.py       чтение изображений и страниц PDF
├── checks/        семь проверок, по файлу на каждую, и общий базовый класс (base.py)
├── config.py      настройки из переменных окружения OCRQ_*
└── errors.py      ошибки и их HTTP-коды
```

**Что происходит с запросом `POST /analyze`:**

1. `api.py` принимает файл. Если он больше лимита, сразу отвечает 413.
2. `services.py` проверяет запрос: известны ли проверки, что за файл (тип определяется по содержимому, а не по имени), не превышены ли лимиты.
3. Если внутри сервиса уже `OCRQ_MAX_REQUESTS` запросов, сервис отвечает 503. Иначе запрос отправляется в пул процессов.
4. В процессе-воркере `analyzer.py`:
   - читает файл (`files.py`);
   - готовит страницу (`page.py`);
   - выполняет запрошенные проверки (`checks/`);
   - считает итог.
   
   PDF обрабатывается страница за страницей.
5. Результат возвращается в основной процесс и уходит клиенту как JSON.

**Почему пул процессов.** Анализ картинки — это около 35 мс чистой работы процессора. Если выполнять его прямо в обработчике запроса, сервер замрёт и задействует только одно ядро. В пуле из N процессов работают все ядра, а сервер тем временем принимает другие запросы.

**Почему `page.py` отдельно от проверок.** Почти всем проверкам нужно одно и то же: найти текст, узнать размер букв, отделить чернила от бумаги. Это считается один раз в `prepare_page`, и проверки получают готовый объект `Page`.

### Как добавить проверку

Создайте файл в `checks/` и допишите экземпляр в `ALL_CHECKS` в `checks/__init__.py`. Остальное (замер времени, статус, перехват ошибок, участие в итоговой оценке) сделает базовый класс:

```python
class GlareCheck(Check):
    """Блики на фотографиях документов."""

    name = "glare"
    unit = "ratio"
    critical = False
    weight = 0.5
    threshold = 0.05

    def measure(self, page: Page) -> Measurement:
        share = float((page.gray[page.document_mask > 0] >= 250).mean())
        return Measurement(value=share, score=ramp(share, bad=0.10, good=0.01),
                           problem=f"glare: {share:.0%} of the page is overexposed")
```

## Проверки

Каждая проверка измеряет одно значение (`value`) и переводит его в оценку `score` от 0 до 1. При значении «плохо» оценка равна 0, при «хорошо» — 1, между ними линейно. Проверка пройдена при `score ≥ 0.5`; `threshold` — значение ровно посередине.

| Проверка | Что меряет | Плохо → хорошо (граница) | Критичная | Вес |
|---|---|---|---|---|
| `blur` | ширина размытия края букв, px, и доля размытых участков текста | 1.4 → 1.0 (1.2 px) | да | 1.5 |
| `skew` | угол строк, ° | 8 → 2 (5°) | да | 1.0 |
| `resolution` | типичная высота буквы в пикселях исходного файла | 4 → 7 (5.5 px) | да | 1.0 |
| `contrast` | (яркость бумаги − яркость чернил) / 255 | 0.04 → 0.16 (0.10) | да | 1.0 |
| `text_presence` | сколько символов сложилось в строки | 10 → 60 (35) | да | 1.0 |
| `exposure` | яркость бумаги и чернил | бумага 70 → 140, чернила 235 → 195 | нет | 0.5 |
| `noise` | пылинок на мегапиксель и зернистость фона | 30 000 → 3 000, σ 12 → 4 | нет | 0.5 |

Если на странице нет текста, проверки, которым он нужен, возвращают `not_applicable`. Например, для фотографии оленя сервис не будет выдумывать угол наклона строк; об отсутствии текста сообщит `text_presence`.

### Как находится текст (`page.py`)

1. Большая картинка уменьшается до 2048 px по длинной стороне.
2. **Чернила** — пиксели, которые темнее среднего по окну 31×31. Такой локальный порог не сбивается от теней и серого фона.
3. Чернила разбиваются на пятна. **Похожими на буквы** считаются пятна подходящего размера и формы.
4. Определяется **типичная высота буквы**: пик гистограммы высот, взвешенной по площади. Без взвешивания тысячи пылинок фактуры стола на фото чека перевешивали настоящие буквы.
5. Соседние буквы **склеиваются в строки**. Текстом считаются только строки из трёх и больше символов, так отсеиваются пыль, фактура и рисунки.
6. Страница делится на **тайлы**: квадраты стороной около шести высот буквы. Отмечаются тайлы с текстом.
7. Определяется **область документа** (тайлы с текстом и отступ вокруг), **бумага** и **яркость чернил и бумаги**.

### Коротко о каждой проверке

- **`blur`.** У размытого края перепад яркости растянут. По самому крутому перепаду в каждом текстовом тайле восстанавливается ширина размытия в пикселях. Такая оценка не зависит ни от контраста, ни от количества текста; классическая дисперсия лапласиана зависит от обоих и путает разреженную чёткую страницу с размытой. Итог — худшее из медианной ширины и доли размытых тайлов, поэтому частичное размытие тоже ловится.
- **`skew`.** Перебираются углы от −45° до 45°. Для каждого угла центры букв проецируются поперёк строк; при верном угле они собираются в острые пики. Сначала поиск идёт с шагом 0,5°, потом уточняется с шагом 0,05°.
- **`resolution`.** DPI в файлах обычно нет (в наборе данных его нет ни у одного файла), а для OCR важно, сколько пикселей приходится на букву. Поэтому меряется типичная высота одиночной буквы в пикселях исходного файла.
- **`contrast`.** Сравниваются сердцевины штрихов с бумагой рядом с ними, только в текстовых областях. Фото и поля на результат не влияют.
- **`exposure`.** Не слишком ли тёмная бумага и не выцвели ли чернила.
- **`noise`.** Пылинки вдали от текста и зернистость бумаги (метод Immerkaer). Считается только в области документа, так что фактура стола на фото чека шумом не считается.
- **`text_presence`.** Сколько символов сложилось в строки.

## Итоговая оценка

```
quality_score = взвешенное геометрическое среднее оценок проверок
                (оценки ниже 0.1 приравниваются к 0.1)

suitable_for_ocr = нет проваленных критичных проверок
                   И ни одна проверка не упала с ошибкой
                   И quality_score >= 0.6
```

- **Почему геометрическое среднее.** Для OCR одно очень плохое свойство (например, сильное размытие) портит всё, как бы хороши ни были остальные. Арифметическое среднее это сгладило бы.
- **Почему пол 0.1.** Без него один ноль обнулял бы всю оценку, а некритичный дефект (шум) должен её снижать, а не уничтожать.
- **PDF.** Страницы без текста (обложки, фото) не учитываются. Документ пригоден, если пригодны все остальные страницы. Оценка документа — среднее по ним. Номера плохих страниц перечислены в `summary.problem_pages`.

## API

| Метод | Что делает |
|---|---|
| `GET /checks` | `{"checks": [...]}` — все доступные проверки |
| `POST /analyze` | multipart: `file` (обязательно) и `checks` (необязательно, через запятую или повтором поля; если не указано — все) |
| `GET /health` | жив ли сервис и сколько запросов внутри |
| `GET /docs` | Swagger |

**Ответ для изображения:** `input`, `suitable_for_ocr`, `quality_score`, `processing_time_ms`, `issues`, `checks` и `timings`. Внутри `checks` для каждой проверки: `passed`, `score`, `status`, `critical`, `weight`, `value`, `unit`, `threshold`, `message`, `details`, `time_ms`.

**Ответ для PDF:** те же поля верхнего уровня, `summary` (номера пригодных, проблемных и пустых страниц) и `pages` (полный результат по каждой странице).

**Ошибки** приходят в одном формате: `{"error": {"code", "message", "details"}}`.

| HTTP | `code` | Когда |
|---|---|---|
| 400 | `invalid_input` | нет файла или файл пустой |
| 413 | `payload_too_large` | файл больше лимита, картинка больше 60 Мп или в PDF больше 200 страниц |
| 415 | `unsupported_media_type` | не изображение и не PDF |
| 422 | `unknown_checks` | неизвестная проверка (в `details` — список доступных) |
| 422 | `corrupted_file` | файл повреждён или PDF под паролем |
| 503 | `overloaded` | сервис занят, повторить позже (заголовок `Retry-After`) |
| 504 | `timeout` | анализ не уложился во время |
| 500 | `worker_crashed` | процесс-воркер упал; пул пересоздан, сервис работает дальше |

## Производительность

Скрипт `scripts/benchmark.py` (`make bench` и `make bench-http`) сам описывает машину и печатает таблицы.

**Окружение:** Apple M5 (10 ядер: 4 производительных и 6 энергоэффективных), 16 ГиБ RAM, macOS 26, Python 3.12. Нагрузочный клиент работает на той же машине, открыты обычные фоновые приложения; разброс между прогонами 15–25%.

### Одно изображение, без HTTP

50 изображений набора данных × 5 прогонов, все 7 проверок, один процесс:

| Стадия | среднее, мс | p95, мс |
|---|---|---|
| чтение и декодирование файла | 9.6 | 42.8 |
| подготовка страницы (поиск текста, тайлы, яркость) | 14.3 | 23.0 |
| все 7 проверок | 12.1 | 19.3 |
| **итого на изображение** | **36.0** | **79.1** |

Самые дорогие проверки: `blur` (8.5 мс), `noise` (2.4 мс) и `skew` (1.2 мс), остальные — меньше 0.1 мс. На пуле из 10 процессов получается **135 изображений в секунду**.

| Одновременных клиентов | успешных запросов/с | задержка принятых, мс | отказов 503 | пик памяти, MiB |
|---|---|---|---|---|

**Выводы:**
- **Потолок около 130–135 изображений в секунду** достигается уже при 8–16 клиентах. Дальше растёт только задержка: запросы ждут свободного процесса.
- **HTTP почти ничего не добавляет:** одно изображение по HTTP занимает 39 мс против 36 мс без него.
- **PDF одним клиентом — 29 страниц в секунду**, потому что документ считается одним процессом страница за страницей. Несколько документов одновременно используют все ядра: 131 страница в секунду.
- **Под перегрузкой сервис отказывает лишним, а не тонет.** При 32 клиентах на 12 мест пропускная способность не падает, принятые запросы обслуживаются за ~94 мс, остальные сразу получают 503. Память ограничена.
- **Ускорение ×4–5 на 10 ядрах, а не ×10.** Только 4 ядра производительные, остальные 6 — энергоэффективные.

## Как сервис держит нагрузку

- **Пул процессов.** Проверки считаются в `OCRQ_WORKERS` процессах (по умолчанию по числу ядер). В каждом процессе OpenCV ограничен одним потоком, чтобы процессы не мешали друг другу.
- **Лимит запросов.** Внутри сервиса одновременно не больше `OCRQ_MAX_REQUESTS` запросов (по умолчанию 4 на каждый воркер): одни считаются, остальные ждут свободного процесса. Следующие сразу получают 503 с `Retry-After`. Поэтому очередь и память не растут без предела: память главного процесса не больше `OCRQ_MAX_REQUESTS × OCRQ_MAX_UPLOAD_MB`, плюс примерно 200 МиБ на каждый воркер.
- **Тайм-аут.** Если анализ идёт дольше `OCRQ_REQUEST_TIMEOUT_S`, клиент получает 504.
- **Падение воркера.** Если процесс-воркер умер (например, его убила система из-за памяти), пул создаётся заново, запрос получает 500, а сервис продолжает работать.

### Сознательные упрощения

Код намеренно сделан простым ценой части производительности:

- **PDF обрабатывается одним процессом**, страница за страницей. Несколько PDF при этом обрабатываются параллельно на разных процессах.
- **Ответ 503 приходит после загрузки файла.** Сервис проверяет загрузку уже после того, как FastAPI принял файл. Для файлов в десятки мегабайт это лишний трафик, но кода заметно меньше.
- **Подготовка страницы считается целиком**, даже если запрошена одна проверка.

| OpenCV, NumPy | обработка изображений |
| Pillow | чтение заголовков изображений, прозрачность |
| pypdfium2 | чтение PDF; лицензия Apache/BSD (у PyMuPDF AGPL) |
| pytest, ruff, mypy | тесты, стиль и обязательные docstring, типы |
| psutil | замер памяти в benchmark |
| Docker | запуск в контейнере с лимитами CPU и памяти |
| Tesseract (в Docker, только для калибровки) | эталон «настоящего OCR» для выбора порогов, в сервис не входит |

## Известные ограничения

- **Поворот на 90° и 180° не определяется:** наклон ищется в пределах ±45°.
- **Перспектива на фото, блики и перекрытия** отдельно не проверяются.
- **Матричная печать** (точечные буквы, image_024) оценивается хуже.
- **Полностью размытые куски текста не видны `blur`:** нечитаемый текст не распознаётся как текст. Так задумано, чтобы не штрафовать анонимизированные поля чеков.
- **Пороги подобраны** на небольшом наборе данных и под Tesseract. Для другого OCR-движка их нужно перекалибровать: это константы в начале файлов проверок.
- **PDF с текстовым слоем** анализируется как картинка.
- **Многостраничный TIFF:** анализируется только первая страница.
- **Тайм-аут не прерывает расчёт** в воркере: тот доработает, и результат будет выброшен.
