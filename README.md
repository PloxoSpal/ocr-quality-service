# OCR Quality Service

HTTP-сервис, который проверяет, пригодно ли изображение документа для OCR. Принимает картинки (PNG, JPEG, WebP, TIFF, BMP) и PDF, возвращает вердикт `suitable_for_ocr`, оценку `quality_score` от 0 до 1, список проблем и результат каждой проверки.

## Быстрый старт

```bash
docker compose up --build
```

Сервис поднимется на <http://localhost:8000>, Swagger доступен на <http://localhost:8000/docs>.

```bash
curl -s -F file=@dataset/images/image_002.jpg localhost:8000/analyze
```

```json
{
  "suitable_for_ocr": false,
  "quality_score": 0.7016,
  "issues": ["skew: text is rotated by -13.4° (limit ±5°)"],
  "checks": {"skew": {"passed": false, "score": 0.0, "value": -13.45, "...": "..."}, "...": "..."},
  "processing_time_ms": 41.2
}
```

Без Docker: `uv sync && make run`. Тесты, оценка на наборе данных и benchmark описаны в [RUNBOOK.md](RUNBOOK.md).

## API

| Метод | Что делает |
|---|---|
| `POST /analyze` | `file` — картинка или PDF; `checks` — необязательно, через запятую (`blur,skew`), по умолчанию все |
| `GET /checks` | список проверок |
| `GET /health` | жив ли сервис |

Для PDF каждая страница проверяется отдельно, в ответе есть `pages` и общий итог `summary`.

Ошибки приходят в виде `{"detail": "..."}`: 400 — пустой файл, 413 — слишком большой, 415 — не картинка и не PDF, 422 — битый файл или неизвестная проверка, 503 — сервис перегружен.

## Проверки

| Проверка | Что меряет | Граница | Критичная |
|---|---|---|---|
| `blur` | ширина размытия края букв | 1.2 px | да |
| `skew` | угол строк | 5° | да |
| `resolution` | высота буквы в пикселях | 5.5 px | да |
| `contrast` | разница яркости чернил и бумаги | 0.10 | да |
| `text_presence` | сколько символов сложилось в строки | 35 | да |
| `exposure` | не слишком ли тёмная бумага или бледные чернила | — | нет |
| `noise` | пылинки и зернистость фона | — | нет |

**Итог.** `quality_score` — взвешенное геометрическое среднее оценок проверок: одно очень плохое свойство портит OCR, как бы хороши ни были остальные. Страница пригодна, если не провалена ни одна критичная проверка и `quality_score >= 0.6`.

**Калибровка.** Пороги подобраны по результатам Tesseract на выданном наборе данных. С ручной разметкой совпадают 46 из 46 изображений (4 пограничных случая не считались), подробности — в `eval/reports/evaluation.md`. Совпадение получено на тех же данных, на которых подбирались пороги.

В отчёте `contrast` не срабатывает ни на одном из 9 изображений с пометкой `low_contrast`, и это ожидаемо: Tesseract читает их хорошо (уверенность 80–86), в разметке они пригодны. Проверка рассчитана на по-настоящему бледный текст: провал на нём проверяет синтетический тест `test_contrast_drops_as_ink_fades`.

## Benchmark

Окружение: Apple M5 (10 ядер), 16 GiB RAM, macOS 26, Python 3.12, без Docker. Данные: 50 изображений из `dataset/images`, все 7 проверок. Повторить: `make bench` и `make bench-http`.

**Один процесс, без HTTP** (50 изображений × 5 прогонов):

| стадия | среднее, мс | p95, мс |
|---|---|---|
| чтение файла | 9.4 | 42.3 |
| поиск текста (`page.py`) | 14.0 | 22.5 |
| 7 проверок | 11.6 | 18.2 |
| **всего на изображение** | **34.9** | 77.0 |

Пул из 10 процессов без HTTP: 147 изображений/с.

**Конкурентная нагрузка по HTTP** (10 процессов, лимит 40 запросов, клиенты шлют изображения без пауз):

| одновременных клиентов | throughput, запросов/с | средняя задержка, мс | p95, мс | отказов 503 | пик памяти, MiB |
|---|---|---|---|---|---|
| 1 | 23 | 43 | 83 | 0 | 1662 |
| 4 | 91 | 43 | 95 | 0 | 2210 |
| 8 | 99 | 76 | 199 | 0 | 2434 |
| 16 | 126 | 111 | 186 | 0 | 2201 |
| 32 | 123 | 223 | 322 | 0 | 2253 |
| 64 | 149 | 256 | 328 | 80 | 2214 |

Throughput упирается в число ядер: после ~16 клиентов растёт только задержка, а сверх лимита запросы получают 503. Память при этом не растёт.

## Модель выполнения

- Один процесс uvicorn принимает запросы и раздаёт файлы пулу из `WORKERS` процессов (`ProcessPoolExecutor`). Анализ занимает процессор, поэтому нужны процессы, а не потоки: из-за GIL потоки не займут все ядра. В воркере OpenCV работает в один поток, чтобы воркеры не мешали друг другу.
- Одновременно в работе не больше `MAX_REQUESTS` запросов (по умолчанию `4 × WORKERS`): часть считается, остальные ждут в очереди пула. Следующие сразу получают 503. Так CPU ограничен числом воркеров, а память — числом запросов.
- Если воркер упал (например, его убила система из-за памяти), запрос получает 500, а пул создаётся заново.

## Технологии

- Python 3.12, FastAPI, uvicorn, pydantic и pydantic-settings — HTTP и формат ответов.
- OpenCV и NumPy — все проверки, без ML-моделей.
- Pillow — чтение заголовков и прозрачных картинок; pypdfium2 — PDF.
- pytest, ruff, mypy, uv, Docker; Tesseract (в Docker) — только чтобы получить эталон для калибровки.

## Как устроено

```
src/ocr_quality/
├── api.py         эндпоинты
├── services.py    пул процессов и лимит запросов (503)
├── analyzer.py    прогон проверок и итоговая оценка
├── page.py        поиск текста на странице: делается один раз для всех проверок
├── files.py       чтение картинок и PDF
├── checks/        по файлу на проверку
├── schemas.py     формат ответов
├── config.py      настройки (WORKERS, MAX_REQUESTS, MAX_UPLOAD_MB)
└── errors.py      ошибки и их HTTP-коды
```

Новая проверка — это класс-наследник `Check` с методом `measure` в `checks/` и одна строка в `ALL_CHECKS`.

## Ограничения

- Поворот на 90° и 180° не определяется: наклон ищется в пределах ±45°.
- Перспектива, блики и перекрытия не проверяются.
- PDF с текстовым слоем анализируется как картинка; у многостраничного TIFF проверяется только первая страница.
- Пороги подобраны на тех же 50 изображениях, на которых оценены; отдельной проверочной выборки нет.
- Весь PDF обрабатывается в одном воркере по странице за раз: документ на 200 страниц надолго занимает один процесс, а остальные ядра ему не помогают.
- Тайм-аута на анализ нет: слишком тяжёлый файл держит воркер до конца.
- Файлы из очереди лежат в памяти целиком: в худшем случае `MAX_REQUESTS × MAX_UPLOAD_MB`.
- Внутри контейнера Python видит все CPU хоста, поэтому `WORKERS` нужно задать равным лимиту CPU (в `docker-compose.yml` это сделано).
- Лимит запросов действует в одном процессе uvicorn; при нескольких репликах лимит у каждой свой.
